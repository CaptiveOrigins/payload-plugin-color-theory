# Decisions

Dated decisions for this repo, newest last.

- 2026-11-09: created from the ops starter kit, area `captive-origins`.
- 2026-11-10: **built at the owner's request**, in Web Platform's chat: "A theme creator with all the different color wheel theory things. It can have some pregenerated themes, and should allow for an easy import export of our json themes with hex. The taxa hierarchy should hook into stuff agnostically, but it should also interface with our theme stuff if possible. So try to use payload's theming structure." Name: the owner suggested `payload-plugin-color-theory` (2026-11-10); confirm before the first publish.
- 2026-11-10 (build): **OKLCH for color math**, so harmonies and scales look even. **Payload's own variables for the admin** (`--color-base-*`, success, warning and error scales), which its light and dark themes already read. **`--palette-*` for sites**, the token names Nested Docs Browser falls back to.
- 2026-11-10 (build): **readable by construction**: text 4.5:1, fills 3:1 against the page and 4.5:1 against their text; colors are moved in lightness only. Every preset, and generated themes from hard base colors, pass in light and dark (tested).
- 2026-11-10 (owner, in Web Platform's chat): "Make sure that the color theory stuff all works with both light and dark themes seamlessly… if so, it should probably be put in color theory". So **light/dark mode lives here** (`/mode`): Auto follows the device live, the choice is kept under `payload-theme` (the website template's key, so existing choices carry over), and the theme CSS adds a `prefers-color-scheme` block for Auto.
- 2026-11-10 (build): **contrast is checked on every surface text can sit on**: page, cards, sunken areas, and for status text its own soft badge fill. The browser trial found links and badges that passed on the page but not on cards or badges.
- 2026-11-10 (build): **the CSS endpoints revalidate** (`no-cache` with an ETag) instead of caching for minutes, so a theme change shows on the next load. The trial showed a stale admin.css after a change.
- 2026-11-10 (build): **one theme per install**, not per site. Per-site themes wait for a real need.
- 2026-11-10 (Helm, checked against ~/Code/CLAUDE.md): **MIT**, Copyright (c) 2026 Captive Origins, as for every general Payload plugin. First-public-push audit: `docs/first-public-push-audit.md` (clean). Going public, the first publish and npm trust are the owner's steps.
- 2026-11-10 (owner, relayed word for word by Helm from Helm's chat): on the bolder-brand mock-up (https://claude.ai/artifact/KznEeG2NLP5nKeA3RjVPPm):
  - Header: "Brown bar with orange rule".
  - Main buttons: "Orange with dark text".
  - Card band: "Let's have a setting in our theme plugin stuff that lets us flip to different levels of the thin colored bands used throughout the site, or however you want to structure that config wise. Let's start with everywhere, but have the option to flick down to varying intensities. If possible, have that slider for other various UI elements so it's like x% of elements on the screen will have this or something (maybe not percentage but you get my point)".
- 2026-11-10 (plan, queued until Helm says resume): **brand intensity**. Named levels (Off, Subtle, Balanced, Bold), one for the whole theme plus optional overrides per element group: card bands, intro washes, badge color, button fills and the header. Each level decides which groups get the brand accent. The levels are saved in the theme JSON (`color-theory/1` stays readable; the new field is optional) and reach the site as CSS variables and data attributes. It starts at Bold (everywhere). Every level must pass WCAG AA, tested the same way as the presets.
- 2026-11-10 (owner, relayed word for word by Helm from Helm's chat): "In our color theory admin thing, it should probably have a little UI kit right next to it so that people can see, in addition to the various color wheel selections, how those apply. We should calculate the WCAG stuff and if they pick something that's too light or too dark, we should put a little icon warning or something over it. Not force them not to, but just says it'd be better for accessibility to be X with this color and jump to that. We could also have a live dynamic little table that shows the wcag scores or something. Maybe it's hidden by default under the UI kit but then as people adjust they can see the live WCAG scores and we can color code them with the number so they can see which elements are failing in the table etc"
- 2026-11-10 (plan, queued with brand intensity; paused until Helm says resume): in the theme editor,
  1. **A live UI kit beside the pickers**, light and dark side by side: header, primary and secondary buttons, links, a card with its band, badges, form fields and alerts. It updates as colors change and follows the brand intensity level.
  2. **A warning icon** on any element whose text and background fail WCAG AA. The tooltip names the nearest passing color ("Better for accessibility: #xxxxxx") and offers "Use this", which moves lightness only. It never blocks: saving still works.
  3. **A live WCAG table**, collapsed under the kit by default: each pair, its ratio, and AA/AAA. The numbers are color-coded (pass, borderline, fail) and also labeled in words. Clicking a row highlights that element in the kit.
  4. **Keyboard and screen readers**: everything works from the keyboard, and results are announced politely, not on every keystroke.
  - **Open question for the owner:** today the tokens move any failing color automatically ("readable by construction"), so the kit would never show a failure. To show warnings without forcing a change, the plan is a per-theme switch: "Adjust colors for accessibility" (on by default, as now) or "Use my exact colors" (warnings shown, nothing moved). Confirm before building.
- 2026-11-10 (owner, relayed word for word by Helm from Helm's chat): on the open question above, he chose "Switch, default adjust (Recommended)". Each theme gets a switch: "Adjust colors for accessibility" (the default, as now) or "Use my exact colors" (warnings and "Use this" are shown, nothing is moved). The switch is saved in the theme JSON as an optional field; themes without it adjust.
- 2026-11-10 (build): brand intensity as **five kinds of element** (button fills, header, badge colors, card bands, intro washes) switched on by level: Subtle 1, Balanced 3, Bold all 5, which approximates the owner's "x% of elements". Exact mode keeps only the **chosen role colors** as they are: text worked out from the neutral (body, muted, header) is always adjusted, because nobody picked it. The intensity slider is a native range input with named steps, so keyboards and screen readers get "Subtle" rather than a number.
- 2026-11-13: moved to the ExtantApe GitHub organization and the `@extantape` npm scope at the same version. EXTANT APE owns its reusable tools and licenses them to the platform. The earlier package name is deprecated with a pointer here, and GitHub redirects the old repository address.
